# 렌더링 이미지로 디자인 방향 고르기

새 발표자료는 목적·청중·사용 환경·형식과 장별 메시지를 정한 뒤 아래 추가 옵션을 제안하고 디자인 후보를 실제 이미지로 보여준다.
사용자가 스타일을 고르거나 선택을 명시적으로 위임한 다음 전체 자료를 제작한다.
선택이 미결이면 자료 확인과 근거 정리는 계속할 수 있지만 전체 덱 생성은 기다린다.
사용자가 이미 확정한 스타일이나 특정 장의 단순 수정은 그 결정을 이어서 적용한다.

## 추가 옵션: 디자인을 고르는 범위

디자인 선택 방식이 아직 없을 때만 다음 질문 하나를 한다.

> 디자인은 어떻게 고르실까요? ① 전체 스타일을 한 번 고르기 ② 주요 페이지만 3안 비교 ③ 모든 페이지를 3안씩 비교

| 선택 | 보여줄 결과 | 안내할 차이 |
|---|---|---|
| 전체 스타일 한 번 선택 | 대표 표지·본문의 스타일 3종 | 빠르게 방향을 정하고 전체 자료에 적용. 별도 요청이 없으면 추천. |
| 주요 페이지만 3안 비교 | 표지·핵심 결과·의사결정 장 등 선택한 페이지마다 3안 | 중요한 장에 집중해 고르기. 대상 장은 현재 목차에서 추천. |
| 모든 페이지 3안 비교 | 전체 장마다 3안 | 각 장을 직접 고르기. N장이면 3N개 시안이라 검토 범위가 커짐. |

선택지 이름과 추천 이유는 사용 목적에 맞춰 쉽게 설명한다. 사용자가 특정 장을 지정하면 그 범위를 따른다. 주요 장의 범위를 정하지 않았으면 목차에서 추천한 장을 짧게 밝히고 진행한다.
전체 스타일 선택은 아래 절차로 진행한다. 주요 장·모든 장 비교는 [페이지별 3안 선택](page-style-selection.md)으로 바로 진행하며 전체 스타일 선택 질문을 추가하지 않는다.
이미 선택·거절했거나 선택을 명시적으로 위임했으면 다시 묻지 않는다. 위임 범위에 디자인이 포함되면 추천 방식을 적용한 이유를 기록한다. 무응답은 선택이나 위임이 아니다.
고정 양식 유지, 단순 문구 수정, 이미 확정한 스타일 재사용에는 이 질문을 끼워 넣지 않는다. 사용자가 나중에 페이지별 비교를 요청하면 해당 장부터 시작하고 완료된 기획 질문을 반복하지 않는다.

## 1. 같은 내용으로 비교

실제 주제의 대표 제목, 핵심 메시지, 항목 2~3개로 표지와 본문을 구성한다.
세 후보가 같은 내용을 담아야 색·정보량·배치의 차이를 비교할 수 있다.
자료가 아직 없으면 예시라는 표시를 붙이고 예시 문장만 사용한다. 실제 성과 수치는 만들지 않는다.

| 후보 | 표현 | 어울리는 상황 |
|---|---|---|
| 01 정돈된 보고형, report | 밝은 지면, 3구역 편집(번호 머리 · 구역별 근거)과 결론 띠 | 회의 보고, 비교, 의사결정 |
| 02 도식 중심 설명형, explain | 노선 — 번호 역을 잇는 흐름, 결과 역 강조, 넉넉한 여백 | 교육, 절차, 개념 설명 |
| 03 메시지 강조형, proposal | 짙은 띠 지면, 큰 메시지, 쉐브론 단계와 다음 행동 강조 | 제안, 핵심 메시지 전달 |

세 방향은 회사 로고·색·서체·머리말·꼬리말·워터마크를 유지하는 본문 구성의 차이다. 세 방향 모두 회사 발표 덱의 디자인 언어(design-language.md)의 배치 문법으로 그린다 — 고른 방향은 본 제작에서 같은 문법을 내용에 맞게 응용하면 시안과 완성본이 이어진다.
사용자가 제공한 별도 참조나 요구가 있으면 그 내용에 맞춰 후보를 조정한다.

## 2. 실제 PNG 생성

스킬 루트의 scripts/style_previews.py를 사용한다. 경로는 사용자 작업 폴더 기준으로 정확히 지정한다.
대표 내용 선정과 아래 입력 파일 작성·실행은 에이전트가 맡는다. 사용자가 JSON을 만들거나 명령을 실행해야 하는 절차로 안내하지 않는다.

```bash
python <스킬루트>/scripts/style_previews.py --content <작업폴더>/style-brief.json --out <작업폴더>/style-review
```

입력 예시:

```json
{
  "title": "조사 결과를 실행으로 연결",
  "message": "핵심 내용을 함께 이해하고 다음 행동을 결정",
  "points": [
    {"label": "핵심 메시지", "detail": "회의에서 공유할 결론"},
    {"label": "판단 근거", "detail": "자료와 비교 기준"},
    {"label": "실행 제안", "detail": "다음 행동과 필요한 결정"}
  ],
  "recommended_style": "report"
}
```

추천 후보는 합의한 목적에 맞게 정하고 이유를 설명한다. recommended_style은 생략 가능하며 선택을 뜻하지 않는다.
출력은 후보별 표지·본문 PNG 6개, 비교 이미지 comparison.png, 개별 HTML과 index.html, styles.json이다.
폰트·로고·발표 엔진을 실제로 적용한 HTML을 브라우저에서 렌더링한다. 추가 AI 이미지 생성 호출은 없다.
렌더링 실패나 내용 넘침이 발생하면 원인을 해결한 뒤 다시 만들고, 실제로 생성되지 않은 이미지를 보여줬다고 말하지 않는다.

## 3. 보여주고 선택 받기

비교 PNG를 대화에 표시하고 개별 원본 이미지와 HTML도 열 수 있게 제공한다.
사용 환경이 이미지 표시를 지원하지 않으면 이미지 파일 경로를 제공하고 그 제한을 밝힌다.
후보별 용도와 차이, 추천 이유를 짧게 설명하고 번호 또는 스타일 이름을 고르는 질문 하나를 한다.
선택형 질문 도구가 있으면 이미지와 함께 활용한다.

응답을 받으면 styles.json의 selected_style에 실제 선택 ID를 기록하고, 최종 제작 방향에도 반영한다.
사용자가 선택을 위임하면 추천 이유와 위임 사실을 함께 기록한다. 무응답을 선택이나 위임으로 간주하지 않는다.
혼합·수정을 원하면 반영한 표지와 본문을 다시 렌더링해 확인할 기회를 준다.

## 4. 형식과 효과의 경계

PNG는 정적인 디자인 비교다. 애니메이션 승인이나 구현 확인을 대신하지 않는다.
움직임은 별도로 정한 방침에 따라 실제 HTML 또는 PPTX 결과에서 검증한다.
이 생성기는 HTML로 디자인 방향을 비교한다. PPTX를 요청받으면 선택한 방향의 실제 PPTX 대표 장을 만들어 렌더링·편집 가능 여부를 확인한 뒤 확대한다.
HTML의 상호작용이나 모든 서체·효과가 PPTX·PDF에서도 동일하게 재현된다고 약속하지 않는다.

## 5. 확정 후 제작

확정한 스타일 ID, 유지할 요소, 조정할 요소를 장별 메시지·형식·효과와 함께 제작 방향에 남긴다.
전체 제작은 이 방향을 따르며 임의로 다른 스타일로 바꾸지 않는다.
