# 비즈니스 발표자료 제작 전 기획 대화

## 적용 범위와 목표

새 발표자료를 만들거나 발표의 목적·대상·메시지를 바꾸는 요청에 적용한다. 사용자가 자기 업무와 자료는 알지만 발표 기획이나 디자인 용어에는 익숙하지 않을 수 있음을 전제로 대화한다.

사용자가 실제로 결정해야 할 항목을 확인하고 선택의 차이를 설명한다. 필요한 선택이 정리되면 그 내용에 맞춰 구성·제작한다. 기존 자료의 오탈자나 특정 슬라이드 한 곳만 고치는 요청은 요청한 수정부터 처리한다.

## 쉽게 시작하고 끝까지 안내하기

“이 자료로 발표자료 만들어 줘”만으로 시작할 수 있다. 에이전트가 제공 파일·링크를 먼저 읽고 이미 알 수 있는 내용은 질문하지 않는다. 읽을 수 없는 자료는 그 제한과 꼭 필요한 부분을 짚는다.
JSON, 경로 구성, 스크립트 명령, 템플릿 이름을 사용자에게 작성·선택하게 하지 않는다. 필요한 작업 파일은 에이전트가 만들고 결과에 영향을 주는 업무 선택만 묻는다.

처음에는 “자료를 확인한 뒤 필요한 것만 여쭙고, 구성과 이미지 시안을 보여드리겠습니다”처럼 다음 행동을 쉽게 설명한다. 사용자가 답을 충분히 주면 질문 목록을 끝까지 읽지 않고 다음 단계로 넘어간다.
“잘 모르겠다”는 선택 위임으로 단정하지 않는다. 목적에 맞는 추천 하나와 이유, 다른 선택의 차이를 설명한다. “나머지는 알아서”처럼 위임하면 그 범위에 추천값을 적용하고 핵심 미결만 질문한다. 무응답은 위임이 아니다.

진행 중에는 현재 확인한 내용과 다음에 보여줄 결과를 한두 문장으로 알린다. 매 답변마다 전체 요구사항을 다시 나열하거나 설정 용어를 설명하지 않는다.

## 1. 먼저 확인하고 첫 질문 고르기

현재 요청, 앞선 대화, 제공 파일과 링크에서 이미 확인된 조건을 정리한다. 자료 파일이 있으면 주제·근거·현재 구성·빠진 정보를 먼저 확인한다. 파일에 있는 결론을 사용자가 원하는 결론이라고 단정하지 않는다.

첫 응답에는 이해한 상황을 짧게 짚고, 결과에 가장 큰 영향을 주는 미결 질문 하나를 한다. 주제 자체가 없으면 어떤 내용의 자료인지 먼저 묻는다. 주제를 알면 발표 목적이나 청중처럼 아직 모르는 항목으로 넘어간다.

질문은 가능하면 선택지 2~3개와 추천안을 함께 제시한다. 사용자가 말로 설명해도 된다. 답변을 받으면 무엇을 이해했고 구성에 어떤 영향을 주는지 설명한 뒤 다음 필요한 질문으로 이어간다. 정해진 질문지를 같은 순서로 끝까지 읽지 않는다.

## 2. 제작 전에 정할 항목

다음 다섯 묶음을 기준으로 누락을 확인하되, 묶음 전체를 한꺼번에 답하게 하지 않는다. 요청·기존 대화로 확정된 값은 그대로 사용한다. 사용자가 위임한 항목은 추천값과 이유를 밝히고 결정한다.

| 결정 묶음 | 확인할 내용 | 자료 제작에 미치는 영향 |
|---|---|---|
| 자료 종류와 목적 | 무엇에 관한 자료인가. 현황 보고·조사 결과 공유·의사결정 요청·제안·교육 중 어떤 역할인가. 청중이 무엇을 이해하거나 결정·실행해야 하는가. | 첫 장의 메시지, 결론 위치, 필요한 근거와 마지막 제안. |
| 청중과 실제 사용 상황 | 누가 보는가. 주제를 얼마나 아는가. 회의실에서 직접 발표하는가, 온라인으로 설명하는가, 파일만 배포하는가. 발표·질의응답 시간과 읽을 환경은 어떤가. | 용어 수준, 설명 깊이, 화면 밀도, 글자 크기, 대본 필요 여부. |
| 내용과 근거 | 제공 자료는 무엇인가. 꼭 넣거나 제외할 내용, 핵심 메시지, 비교 기준은 무엇인가. 추가 조사가 필요한가. 확인된 사실과 제안은 무엇인가. | 장별 주장과 출처, 부족한 근거의 보완, 본문과 부록의 구분. |
| 산출물과 디자인 | 편집 가능한 PPTX인가, 브라우저 발표용 HTML인가, 배포용 PDF인가. 한 형식 또는 복수 형식인가. 회사 양식의 적용 범위, 원하는 분위기, 분량, 마감, 이미지·도표 비중은 어떤가. | 제작 경로, 레이아웃, 편집·공유 방식과 납품 범위. |
| 움직임과 발표 보조 | 애니메이션을 넣는가. 없음·필요한 곳만·적극적인 연출 중 어느 정도인가. 클릭 전개인가, 자동 재생인가. 근거 펼침·확대 같은 상호작용, 발표자 노트·대본이 필요한가. | 효과의 종류와 적용 위치, 발표 조작, 형식별 구현·검증 범위. |

### 반드시 확인할 핵심 선택

자료의 주제·목적, 청중, 실제 용도, 출력 형식, 시간 또는 분량, 애니메이션 방침은 제작 전에 결정된 값이 있어야 한다. 사용자 답변·자료에서 확인한 값과 사용자가 위임해 에이전트가 결정한 값을 구분한다. 모든 사용자가 모든 디자인 수치를 직접 정할 필요는 없다. 이미 확인된 요구로 판단할 수 있는 세부사항은 추천하고 이유를 설명한다.

애니메이션은 사용자가 언급하지 않았다고 자동으로 넣거나 빼지 않는다. 원하는 정도를 묻고, 클릭·자동 재생 선택이 실제로 필요한 경우 작동 방식도 확인한다. 사용자가 전체 방향을 위임하면 그 위임에 따라 추천한다.

HTML·PPTX·PDF가 모두 필요하다고 가정하지 않는다. 편집·발표·배포 목적을 설명하며 필요한 형식을 고르게 한다. 처음부터 PPTX를 원하면 PPTX 경로를 따른다. 장수만 정해졌다면 발표 시간과 청중을 고려해 그 장수로 전달 가능한지 설명한다.

추천은 사용 상황에서 도출한다. 예를 들어 팀장 의사결정용은 결론·비교·권고안과 정돈된 보고형, 신입 교육은 단계·실제 사례와 도식 중심 설명형을 제안할 수 있다. 이는 추천 예시이며 모든 요청에 같은 목차·장수·스타일을 강제하지 않는다.

## 3. 선택을 돕는 설명

질문에는 왜 이 선택이 필요한지 짧게 붙인다. 기술 용어 대신 사용 경험으로 설명한다.

- 목적: “도구를 소개하는 자료와 도입 승인을 받는 자료는 강조할 내용이 달라집니다. 이번 발표에서 어떤 결과를 얻고 싶으신가요?”
- 청중: “주제를 처음 접하는 직원이라면 용어 설명과 사례가 필요합니다. 참석자들은 이 내용을 어느 정도 알고 있나요?”
- 형식: “동료가 PowerPoint에서 고쳐 써야 하면 PPTX가 맞고, 브라우저에서 단계 전개나 근거 펼침을 보여주려면 HTML이 맞습니다. 주로 어떻게 사용하실 예정인가요?”
- 효과: “효과 없이 정적으로, 필요한 곳만 클릭으로 전개, 핵심 장면을 적극적으로 연출하는 방식이 있습니다. 이번 발표에는 어느 정도를 원하시나요?”
- 추천 이유: “팀장에게 도입 판단을 요청하는 목적이므로 업무 문제, 비교 기준, 근거, 권고안 순서가 적합합니다. 기능 소개는 판단에 필요한 만큼 배치하겠습니다.”

예시는 대화의 방식이며 고정 대본이 아니다. 직무·청중·사용자가 방금 설명한 내용을 반영해 질문을 바꾼다. 사용자가 모른다고 하면 구체적인 예와 추천안을 제시한다.

## 4. 제작 방향 정리와 목차 제안

핵심 선택이 정리되면 다음 다섯 줄 안팎으로 제작 방향을 보여준다.

1. 주제·자료 종류·발표 후 기대하는 판단이나 행동.
2. 청중·사용 환경·시간 또는 분량.
3. 자료·출처와 핵심 메시지.
4. 출력 형식·디자인 방향·이미지와 도표 사용.
5. 애니메이션 정도·작동 방식·필요한 발표 보조물.

이어서 장별 핵심 메시지가 있는 목차를 제안하고, 중요한 구성 선택의 이유를 설명한다. 복수 방향이 실제로 유효할 때는 두 안의 차이와 추천안을 보여준다. 사용자가 제안한 결론이나 강조점을 임의로 바꾸지 않는다.

목차를 정리한 뒤 visual-style-selection.md에 따라 스타일 후보를 실제 이미지로 보여주고 선택을 받는다. 핵심 미결이 남아 있으면 해당 선택을 확인하는 질문 하나를 한다. 요청과 답변에 제작 의사가 있고 스타일을 포함한 필요한 선택이 해결됐다면 정리한 방향을 알리고 제작한다. 같은 내용에 대해 별도의 허가를 반복해서 묻지 않는다. 사용자가 목차나 시안을 먼저 검토하겠다고 하면 그 단계에서 의견을 받는다.

### 결정을 기억하는 작업 기록

새 발표자료의 작업 폴더에 blue-report-brief.md 하나로 기획을 기록한다. 기존 기획 문서가 있으면 그것을 갱신해 중복 문서를 만들지 않는다. 문서 작성은 에이전트가 맡으며 사용자가 양식을 채우게 하지 않는다.
주제·목적·청중·사용 상황·형식·시간/분량·효과, 선택한 스타일, 장별 핵심 메시지와 출처, 미결 사항, 최신 파일 위치를 남긴다. 중요한 값에는 사용자 지정·자료에서 확인·위임 후 추천 적용 중 출처를 붙인다. styles.json의 실제 선택과 이 기록을 맞춘다.
후속 수정이나 재개 때는 이 기록과 현재 파일부터 읽는다. 목적·청중이 바뀌지 않으면 완료된 기획 질문을 다시 시작하지 않는다. 개인 선호를 다른 직원의 기본값으로 삼거나 전역 설정에 자동 저장하지 않는다.

## 5. 제작·검수 중에도 기획 의도 유지

디자인과 레이아웃은 회사 규격 안에서 합의한 목적과 사용 환경에 맞춘다. 기준 덱의 견본 장수나 예시 목차를 새 자료의 장수로 강제하지 않는다. 조사 자료는 사실, 해석, 제안과 출처를 구분하고 자료가 뒷받침하지 않는 성과·수치는 채워 넣지 않는다.

움직임은 합의한 방침에 따라 어떤 내용을 언제 드러낼지 정한다. 정적인 배포본은 효과 없이 읽어도 내용이 이어지게 구성한다. 현재 기본 PPTX 생성기는 정적 출력이므로 효과를 요청받으면 실제 제작 경로의 지원 여부를 먼저 확인한다. HTML의 상호작용이 PPTX나 PDF에도 그대로 유지된다고 약속하지 않는다.

수정 의견을 받으면 바꾸려는 메시지와 범위를 확인해 해당 부분을 반영한다. 목적과 청중이 바뀌는 수정은 제작 방향도 함께 갱신하고, 문구 한 곳의 수정이면 전체 기획 질문을 다시 시작하지 않는다.

완료할 때 실제 파일과 검증 결과를 전달하며 합의한 형식, 핵심 메시지, 효과가 어떻게 반영됐는지 짧게 설명한다.
